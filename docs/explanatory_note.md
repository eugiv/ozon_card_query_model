# 1. Введение и постановка задачи

Покупатель маркетплейса может искать не название товара, а задачу, назначение или ситуацию использования. Совпадение слов с названием поэтому не исчерпывает возможные поисковые запросы. Для карточек с малой видимостью полезен короткий список кластеров, который специалист проверит перед изменением текста.

Цель проекта — воспроизводимый поиск и ранжирование связей SKU × normquery с малым наблюдаемым трафиком. Входы: история поисковой видимости и заказов, фиксированный словарь кластеров и, отдельно для текущей выдачи, датированный текст карточки. Выход: упорядоченные гипотезы с источниками, приоритетом и причинами фильтрации. Кластеры задаются WB: проект не создаёт собственную кластеризацию и не дописывает слова к запросам.

Кандидат не имеет наблюдаемых прежних заказов данного SKU во всей доступной прошлой истории и получает 0–5 суммарных просмотров за 14 дней. Окно и порог — параметры эксперимента. Продающие кластеры товара служат ориентирами для новых связей.

Задачи: проверить качество и временную доступность данных; реализовать текстовый, семантический и графовый поиск; обучить CatBoost, семантический адаптер и LightGCN; выбрать метод только на validation; сравнить методы на одинаковой популяции и пуле; отделить историческую оценку от проверки текущего текста.

Система формирует очередь review с основаниями выбора и приоритетом. Ранжирование дополняется проверкой текущего текста, чтобы специалист видел новые предложения и явные противоречия. ClickHouse используется только для чтения.

Практическая ценность — сокращение пространства поиска и объяснимая подготовка кандидатов. Специалист получает приоритетный список с продающими ориентирами и товарными свидетельствами, проверяет пригодность фраз и выбирает доступные текстовые поля. Такой выпуск готов для предметного бизнес-пилота.

# 2. Данные и их особенности

Источник — default_staging.stg_ozon_product_queries_details в ClickHouse, только чтение. Актуальная полная выгрузка: 3 203 109 строк, 2 171 SKU, 09.01–07.10.2026; представлены 268 дней. Строка соответствует дате, товару и исходному запросу. Миллионы фактов нельзя называть миллионами размеченных обучающих примеров.

| Поле | Смысл и ограничение |
|---|---|
| unique_search_users | Пользователи, искавшие исходную фразу; сигнал спроса |
| unique_view_users | Пользователи, увидевшие карточку; просмотры, не клики |
| order_count | Число заказов, не обязательно покупателей |

Суммы по дням и вариантам запросов не являются числом уникальных людей за весь период. Спрос сначала дедуплицируется максимумом по дню и исходной фразе, без повторного суммирования по SKU. Заказы сохраняют связь с конкретным товаром.

Исторический снимок raw.wb_normquery зафиксирован на конец 26.06.2026 UTC: 477 579 кластеров. Покрытие заказов — 82,24%: 191 456 из 232 791, точная доля 0,8224372935379805 по аудиту текущей оценки. Несопоставленные записи не становятся отрицательными ответами. loaded_at задаёт доступность записи, не известную версию алгоритма WB.

Отсутствуют 19.05, 04.06, 12.06 и 21.07.2026. Такие дни не подменяются нулями; неполные окна ответов и недавних просмотров исключаются. Строки на остальных датах не доказывают полноту загрузки внутри дня.

Дубликаты date + sku + query и некорректные счётчики отклоняются. Полные выгрузки, тексты и embeddings остаются приватными локальными входами. Синтетические проверки не требуют базы или секретов: они проверяют код, а не измеряют реальное качество рекомендаций.

# 3. Что измеряет эксперимент: данные и временной контроль

Фразы приводятся к нижнему регистру с обрезкой внешних пробелов. Из успешных непустых соответствий выбирается последнее с loaded_at не позднее снимка; ничья разрешается по normquery. Один query получает один кластер: заказы не размножаются.

Факты агрегируются до SKU × normquery. На дату решения доступны только прошлые факты. Прежние продающие связи исключаются из новых кандидатов; фильтр 0–5 просмотров за последние 14 дней применяется до бюджета поиска.

| Часть | Дата решения | Период ответов |
|---|---|---|
| Train | 26.06.2026 | 27.06–10.07.2026 |
| Train | 03.07.2026 | 04–17.07.2026 |
| Train | 07.08.2026 | 08–21.08.2026 |
| Train | 14.08.2026 | 15–28.08.2026 |
| Train | 21.08.2026 | 22.08–04.09.2026 |
| Validation | 04.09.2026 | 05–18.09.2026 |
| Test: диагностика | 18.09.2026 | 19.09–02.10.2026 |
| Новые четыре дня | 03.10.2026 | 04–07.10.2026 |

Шаг train — 7 дней: перекрывающиеся ответы не являются независимыми наблюдениями. Решения 10.07, 17.07, 24.07, 31.07 исключены из-за пропуска 21.07. Январская история служит июньским контекстом, не январским benchmark с будущим словарём.

Проверочные адаптер и LightGCN обучены по 04.09. Validation выбирает итерации, веса и метод; test уже просмотрен и остаётся диагностическим: не независимое подтверждение. Новые четыре дня дают разницу +2,81 п.п., 95%: −2,08…+7,92 п.п.; интервал включает ноль, полного горизонта нет.

Отдельный refit по 07.10 включает прежние ответы: сентябрьские метрики оценивают проверочные модели, не финальный выпуск. Октябрьский текст используется только для текущего отсева, не для сентябрьских признаков.

Цель — найти наблюдаемые будущие продающие связи. Precision — proxy заказов, не экспертная релевантность: остальные 95,04% десятки не объявляются неподходящими. Мало просмотров не доказывает отсутствия фразы. Ограничения: полнота загрузки неизвестна, алгоритм WB неизвестен, нужны продающие ориентиры; холодный старт не решён. Фото и OCR в текущем решении не использовались; фото/OCR вне текущего объёма. Изменений карточек и измеренного бизнес-прироста нет.

Стресс проверяет сохранённый пул без переобучения: искусственные возмущения, не опечатки и не повреждение источника. Не доказывает устойчивость всей системы. Товарная пригодность и эффект SEO требуют отдельного аудита и бизнес-эксперимента.

# 4. Варианты решения и архитектура

| Компонент | Роль и способ использования |
|---|---|
| TF-IDF | Контрольный лексический поиск, символьные n-граммы 3–5 |
| E5 | Предобученная multilingual-e5-small; готовые веса используются без изменения |
| Co-sales | Поведенческий канал, рассчитываемый из наблюдаемых совместных продаж |
| Адаптер | Residual MLP над векторами E5; обучен на данных проекта, 15 эпох |
| LightGCN | Графовая нейросеть SKU ↔ кластер; обучена на данных проекта, 30 эпох |
| CatBoost PairLogit | Обученный попарный ранжировщик, 600 итераций; сравнивается с гибридом |
| RRF / learned fusion | Итоговое объединение четырёх каналов; веса выбраны на validation |

TF-IDF прост и воспроизводим, но пропускает смысловую близость; E5 расширяет семантический поиск. Co-sales переносит наблюдаемые связи, обученные каналы адаптируют представления к истории. Популярность — контроль без персонализации, не свидетельство пригодности товара.

До 150 допустимых кандидатов на канал объединяются без дублей с сохранением признаков и происхождения. Текстовые каналы используют до 32 продающих ориентиров; запрет прошлых продаж — все связи. LightGCN строит профиль из seed-кластеров, не собственного SKU embedding; неизвестный графу кластер не считается плохим.

RRF: `score = Σ w / (60 + rank)`. По validation NDCG@10 выбран гибрид: 25% E5 + 25% co-sales + 25% адаптер + 25% LightGCN. Это ранговый приоритет, не вероятность. CatBoost сохранён как обученный альтернативный ранжировщик. Cross-encoder и GraphSAGE — дальнейшие эксперименты.

Контур: подготовка → поиск → обучение → validation → диагностика и ablation → отдельный refit → товарный отсев → review. Структура: 9 ML-модулей в src, один модуль материалов tools/defense.py, config.json и requirements.txt. Материалы собираются через .venv/bin/python -m tools.defense note; личный гайд — через .venv/bin/python -m tools.defense guide.

Единый запуск: .venv/bin/python src/recommender.py run --config config.json.

Проверка: .venv/bin/python src/recommender.py verify --config config.json.

Готовая выдача без переобучения: .venv/bin/python src/recommender.py recommend --release reports/stage3_release --as-of 2026-10-11T01:28:00Z --output reports/recommendations_new.

# 5. Обучение и критерии оценки

CatBoost решает две задачи: новый заказ малотрафиковой связи в следующие 14 дней и восстановление скрытого продающего кластера. При скрытии удаляется вся собственная связь SKU из истории, просмотров и исходного графа; прошлые продажи у других SKU допустимы. На решение формируются две задачи восстановления.

Положительные цели не внедряются в пул принудительно. На найденный positive берётся до 12 неизвестных сравнений: сложных близких и seeded-случайных. PairLogit поднимает наблюдаемый positive выше unknown; это эвристическое positive–unlabelled ранжирование. Вес пары `1 / (число positives × число сравнений)` нормирует группу SKU–задача.

Признаки CatBoost: текстовая/E5-близость, co-sales, глобальные продажи и спрос, ранги каналов. Собственные просмотры, поиски и дни активности не задают приоритет. Проверочная модель: 37 245 строк, 334 SKU, 2 504 группы; из 100/300/600 выбрано 600 итераций на validation. Финальный refit: 46 787 строк, 413 SKU, 3 053 группы.

Адаптер: `normalize(x + 0,1 × MLP(x))`, 384 → 128 → 384, ReLU, InfoNCE, 15 эпох. Positive — co-sale пара, до 64 пар/SKU с нормированным весом. Одинаковые фразы и известные co-sale пары исключены из слабых batch-сравнений. Готовые веса E5 фиксированы; обучается MLP-поправка. Финальный refit: 23 569 пар, 589 SKU.

LightGCN: 32 измерения, 2 слоя нормированной передачи сообщений, BPR и L2, 30 эпох; 9 525 проверочных и 10 742 финальных продающих рёбер. Обученные представления проверяются по будущим заказам, не по скрытым ранее виденным рёбрам. Mask-and-recover относится к исходному контуру со скрытой историей.

Метрики — macro по SKU с положительными ответами, включая пустую выдачу. `Recall@K = H/P`; `Precision@K = H/K`, короткая выдача тоже делится на K. `NDCG@K = DCG/IDCG`, `DCG = Σ rᵢ/log₂(i+1)`. Пропущенные поиском цели остаются в знаменателе Recall; полнота пула измеряется отдельно.

Seed 7 фиксирует случайные сравнения. Контрольные суммы связывают входы и результаты восьми этапов; verify пересчитывает метрики по сохранённым прогнозам. Проверки на синтетике обучают настоящие модели и проверяют работоспособность, не бизнес-качество.

# 6. Результаты и практическое применение

Диагностический test: одинаковая популяция 121 SKU, 260 будущих положительных связей, один расширенный пул 166 291 кандидатов. Полнота поиска пула — 73,13%; пропущенные цели сохранены в знаменателях.

| Метод | Recall@10 | Precision@10, proxy | NDCG@10 |
|---|---:|---:|---:|
| TF-IDF | 9,11% | 1,74% | 0,0520 |
| Co-sales | 12,87% | 3,14% | 0,0976 |
| Предобученная E5 | 11,90% | 2,56% | 0,0767 |
| Обученный адаптер | 12,89% | 2,81% | 0,0932 |
| LightGCN | 15,17% | 3,72% | 0,1024 |
| CatBoost | 15,29% | 3,64% | 0,0964 |
| Гибрид четырёх | 22,85% | 4,96% | 0,1622 |

На срезе нулевых прошлых просмотров: 94 SKU, 180 положительных целей, гибрид Recall@10 16,83%. Новые 04–07.10: 96 SKU, 132 цели; контроль 15,14%, гибрид 17,95%.

Текущая очередь после отдельного refit: 3 530 review-связей для 353 SKU из 212 787 кандидатов, максимум 10 на товар. Во всём пуле заблокированы 27 055 явных конфликтов, 907 фраз уже найдены в тексте. Это не измерение качества top-10. Дата выдачи — 11.10, трафик по 07.10, текст — снимок 06.10.2026.

Товарная политика — объяснимые правила для человека, не прогноз заказа и не список исключений по SKU. Проверяются непрерывная фраза и явные противоречия по ограниченному словарю. Нет конфликта означает not_verified; автоматическое add_candidate не создаётся. Основание и свидетельства помогают специалисту принять решение.

Стресс ранжирования выполнен без обучения и подбора весов. Три повтора, seed 7/8/9: Recall@10 исходно 22,85%; шум оценок 5% — 23,03%, 15% — 22,41%; счётчики ×100 у 1% кандидатов — 21,47%; случайная потеря 10%/30% пула — 20,26%/17,61%. Шум масштабирован стандартным отклонением оценок внутри SKU; правильные ответы неизменны, потерянные цели остаются в знаменателе. Расчёт: src/recommender.py results; агрегаты — reports/stage4_results/metrics.json.

Практический результат — короткая воспроизводимая очередь. Специалист проверяет карточку, выбирает подходящие фразы и доступные SEO-поля, фиксирует решение. Поиск и подготовка очереди уже выполнены программой.

# 7. Заключение и направления развития

Цель достигнута: создана работоспособная воспроизводимая гибридная рекомендательная система. По продающим ориентирам SKU она находит отдельные малотрафиковые normquery. Обучены CatBoost, адаптер и LightGCN; гибрид выбран на validation. Сохранённые модели воспроизводят выдачу: 3 530 приоритетных предложений для 353 товаров.

Вклад обучения на одном пуле: E5 + co-sales — 19,06% Recall@10; + адаптер — 21,59%; + LightGCN — 20,90%; все четыре — 22,85%. Прирост +3,79 п.п., или +19,89% относительно контроля по точным агрегатам; парный SKU-bootstrap, 2 000 повторов, seed 7, 95%: +0,20…+7,57 п.п. Обученные каналы дали измеримый выигрыш. Границы оценки собраны в разделе «Что измеряет эксперимент».

Результат готов для следующего бизнес-решения: зафиксировать версию, провести товарный аудит приоритетной очереди и проверить выпуск на новом полном периоде. Специалист получает не весь словарь, а объяснимый короткий список; команда сохраняет проверяемое сравнение версий.

Потери: 22,85% целей — в десятке, 23,02% — на местах 11–50, 27,26% — ниже 50, 26,87% не найдены. Это macro-доли по 121 SKU, не доли от 260 связей. При шуме 15% сохраняется 67,36% десятки: список чувствителен к сигналам.

| Приоритет | Следующий эксперимент | Как оценить |
|---|---|---|
| 1. Независимость | Зафиксировать версию; проверить новый полный период | Recall, NDCG, интервал разницы |
| 2. Поиск и порядок | Расширить поиск; испытать точное ранжирование | Полнота пула, NDCG, вклад изменений |
| 3. Совместимость | Расширить проверку свойств; провести аудит | Подходящие фразы, конфликты и неизвестные отдельно |

Дальнейшая работа привязана к измеренным потерям: повысить полноту поиска, поднять найденные цели в десятку, расширить проверку свойств и сохранить человеческий контроль. Отдельный A/B-пилот изменений карточек позволит оценить бизнес-эффект. Новые архитектуры исследуются после фиксации контрольного результата.

Для сдачи заполните реквизиты и зафиксируйте ссылку на конкретный коммит [репозитория](https://github.com/eugiv/ozon_card_query_model). Публичная копия не содержит .env, приватных данных и весов.
